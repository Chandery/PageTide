# Stage 与任务执行计划

数字事实源：`harness/tasks.json`（依赖、状态、验收与证据），`harness/requirements.json` → `harness/evaluations.json`（需求到 gate）。本页只解释顺序，避免复制一份会漂移的完成清单。

| 阶段 | 工作包 | Gate / 何时停止重做 |
|---|---|---|
| 0 | S0-01～03：brainstorm、调研、审查、可复算预算、项目harness | 文档/预算/任务/测试自洽；用户确认预算与前置条件。当前是此阶段交付，不是app完成 |
| A | A-01～06：低配原型、SQLite、PDF批注、网关、问答 | PDF定位/恢复、性能、token计数/实际API校准。若不达标先缩scope或改架构 |
| B | B-01～04：一个领域数据源、去重、词法排序、五卡与反馈 | 数据覆盖及日期正确；五卡成本与质量可接受；缓存/失败有界 |
| C | C-01～04：画像/MMR、周报、轻量与暂停 | 相比关键词基线有帮助、不把忙当不喜欢、不形成未读债务 |
| D | D-01～04：备份恢复、预算故障、安全性能、安装发布 | 所有blocking eval真实通过；独立review与发布批准 |

A/B 可有部分并行（比如领域调研和阅读原型），但首次真实模型调用绝不能先于 A-04 预算网关和 A-05 授权。D 是全链路加固，不是首次做数据安全/预算的阶段。

## 每个工作单元

1. 从任务 JSON 选一个依赖满足的任务，读取相关 requirement / evaluation。
2. 新功能先取得该切片的批准；标 in_progress，记录范围、假设与预算。
3. 一个可验收切片、一个 change record；实现过程用该 record 累积证据，不给每一行代码创建文档。
4. 行为变化先有回归场景；验证失败保存失败证据，不标 done。
5. 完成依据是验收证据，不是代码文件存在；任务 done 要有 evidence。
6. 跨 agent 接手只需 AGENTS → HANDOFF → 当前任务/变更/相关设计，不读整个历史。

## 风险前置

- A-01 先测 Electron 基础占用，A-03 先测真实双栏 PDF 的选区恢复。
- A-04 先fake provider验证预留/核账，再付费校准，付费样本和总量单独批准。
- B-01 领域未知则blocked，不能随手选CS论文宣称满足用户方向。
- C-02 标注数据不够则not_run，不能把点击增加当成推荐质量提升。
- D-01 必须从备份恢复到新目录验证，不能只看“备份文件生成了”。

当前不提供虚假的完成日期；前置风险试验后再给迭代工期。所有 A/B/C/D 都包含在目标范围中。
