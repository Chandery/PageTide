# 项目 Harness：约束、记录、审查、验证与交接

本 harness 是项目自己的少量文件与离线CLI，不是自动多agent运行平台。知识源是repo；AGENTS负责导航；skill负责流程；JSON负责可检查事实；脚本和测试负责机械约束；实际app测试负责产品证据。

## 1. 哪些能力现在有，哪些没有

已经提供：预算算术/生成表漂移检查、模型操作和prompt登记检查、需求→任务→eval链接、任务依赖环/无证据完成检查、文档链接、来源复查日期、改动路径最低风险分类、变更记录覆盖范围、unit tests。

尚未提供：应用代码、TypeScript lint、app端模型调用扫描、SQLite预算预留实现、真实tokenizer、付费eval、PDF自动化、内存基准、安装包CI。这些是A/B/C/D任务，不是当前CLI暗中已经实现的功能。

当前CLI能检查记录是否自洽，不能证明证据真实、输出高质量、代码无漏洞，不能防止有意绕过规则的agent。重要结论仍需独立review；权限和账单边界最终由实际运行环境/应用/服务商控制。

## 2. 目录分工

- `AGENTS.md`：短入口，按需链接文档与四个项目skill。
- `docs/PRODUCT.md` / `ARCHITECTURE.md`：设计、边界和非目标。
- `docs/decisions/`：只记重要长期选择；保留历史，用新ADR supersede。
- `harness/requirements.json` / `tasks.json` / `evaluations.json`：需求、状态、依赖、验收和证据。
- `harness/budget.json`：所有LLM操作、频率/输入输出假设、价格、阈值及批准状态。
- `harness/sources.json`：外部事实出处与复查期限；日期不是语义正确性的替代品。
- `prompts/`：版本化的草案，每个文件必须对应budget operation。
- `changes/`：每个完整工作单元一条JSON记录，支持实际变更路径核对。
- `docs/evidence/`：脱敏检查输出与独立审查，不存私人论文库/真实usage原文。
- `docs/HANDOFF.md`：下一agent需要的最小当前状态。

## 3. 风险分级，不按代码行数

| 级别 | 例子 | 必需记录/验证 |
|---|---|---|
| docs | README措辞/拼写，不涉及规则或合同 | 短change record、链接检查、diff review；无需ADR/付费eval |
| standard | 不改架构边界的普通bug | 任务/需求、回归测试、有关检查、预算零变化的理由、自审 |
| feature | 新增可观察行为 | 批准的验收、stage task、失败状态、eval、数据/隐私/资源/预算审查、相关docs、独立review（发布前） |
| critical | prompt/model/预算、IPC、迁移/删除/备份、harness规则 | 上述 + 合同变化/恢复策略、适用ADR、独立review与发布批准 |

一个工作单元可含多次修正和多个文件，不要求每改一行写一份文档。不要为了刷新时间戳改无关文档。语义风险可能高于脚本按路径推断的最低级别；例如未落在已知目录的新provider也必须手工标critical。

## 4. 日常闭环

1. 接手：AGENTS → HANDOFF → 当前task与相关设计。核实Git；脏工作区不要覆盖。
2. 规划：定义用户结果和不做什么，枚举token/网络/数据/资源影响。变更预算或新付费调用先批准。
3. 实现：小切片、先回归场景；新模型行为从fake provider开始。
4. 检查：本地快速检查→相关功能测试→必要的macOS/故障/付费合同测试。
5. 审查两遍：是否满足规格；实现质量/边界是否正确。复杂或高风险用独立reviewer，不用无限agent群。
6. 记录：更新一条change record、相关任务/文档/预算；未满足gate如实保留not_run/blocked。
7. 交接：写清完成与未完成、执行过的命令和证据、下一步。新的agent不必读取旧聊天。

reviewer不得只看实施者总结，应查看实际diff/关键调用链/测试与失效场景。review之后的行为改动使相关review证据失效，需要复核。

## 5. 命令与实际约束

```sh
python3 scripts/budget.py --write
python3 scripts/budget.py --check
python3 scripts/harness.py check
python3 -m unittest discover -s tests -v
npm run test:app
python3 scripts/harness.py impact
python3 scripts/harness.py review changes/<id>.json
```

`impact`检查tracked、staged、untracked的路径，rename按删除+新增考虑。`review`要求record.files恰好覆盖整个当前改动集；它不猜测哪个改动属于哪个任务。多个工作单元混在一起时，先commit/隔离，或明确作为一个review单元，不要谎填文件列表。

创建record参考 `harness/templates/change.json`。每条check必须标记已注册的category与对应命令：docs至少`repository`，standard再加`tests`，feature/critical还需要`budget`；当前注册命令在`scripts/harness.py`的`CHECK_COMMANDS`，新增测试体系时一并评审扩展。证据必须是`docs/evidence/`内非空文件，不能拿`true`和README替代测试。

预算impact必须区分`zero`、`changed`、`not_applicable`；非docs记录before/after；`changed`还要求同周期的量化input/output/USD。注册表仅验证结构，不认证人工签字，也不重新执行记录中的任意命令。所有批准/完成开关必须是JSON布尔值，字符串`"false"`不能放行。用户批准字段不可由agent自填。

严格外部资料复查：`python3 scripts/harness.py check --strict-freshness`。日常离线可给过期警告；发布/付费测试前必须更新事实出处，不能单纯改verified_on。

发布：`python3 scripts/harness.py check --release` 与 `review ... --release`。当前预计失败，因为app尚未实现、gate未运行、用户未批准。不能把这个失败当成harness缺陷或放宽检查。

可选Git hook示例在 `.githooks/pre-commit`，未自动启用。用户同意后可以配置；无远程仓库故当前没有实际CI。A-01设置app package scripts，后续远程CI应调用同一命令，禁止另写一套不同规则。

## 6. 动态预算与知识新鲜度

提示文本、模型、默认thinking、上下文、schema、工具、频率、重试、缓存失效策略、外发数据变化都触发audit-budget。更新JSON后重算生成表并review diff；金额和token两个维度同时看。当前实测unknown，不能填0掩盖。

资料更新触发：相关代码/合同变化时；每个stage结束；发布前；价格/协议至少30天复查。文档过期且尚未证实的断言标为假设或删除，不让旧记忆覆盖当前源。依赖/许可审查在引入时做，发布时再查，不能只依赖stars。

源代码的架构/调用扫描要在src存在时加入；不能用一个查不到任何代码的规则宣称“无旁路”已通过。fixture质量和验收阈值调整是可见的critical变更，不能为了绿灯降低标准。

## 7. 最小知识与agent成本

无需向量知识库。先用结构化ID、普通文件链接、rg/文本搜索和Git历史。只加载当前任务相关文档；长日志只保留路径/摘要，不反复塞进提示。

默认一个实施agent；feature/critical增加一次独立review。两次修复循环后重新规划而非无界重试。开发agent软预算与运行时预算分离；缺少宿主计数时如实unknown。此harness支持流程约束，不声称能控制所有agent客户端的计费和权限。
