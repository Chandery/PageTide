# ADR 0028: complete growth judgments and explicit reply validation

2026-10-07. User reported stopped0/16 and2/17 after switching to the whole-queue app. A registered real diagnostic request reproduced new_task/new_branch replies carrying an ordinary topic name in the join-only direction field. The generic example included that field without defining its exclusive meaning, so local validation discarded otherwise usable opinions and stopped the job. Exact historical response text was not persisted and is not reconstructed as fact.

Use verdict-specific minimal output formats. New proposals use name; only join uses a d alias in direction. For compatibility, a new proposal's optional direction can be a <=40-character validUTF8 display label; it must not contain p/c/d aliases or actual input/local identifiers. The label cannot merge proposals, add an edge, choose a target or bypass other validation. Nearest, parent, needs, required_by, terms and lengths remain strict. Reuse strict_json to reject duplicate keys/nonfinite numbers. Validate all prose/terms asUTF8 before hashing/SQLite. Report stable local field/JSON/truncation/missing/duplicate/topology reasons, and preserve valid saved opinions on partial failure. No raw replies or private identifiers in diagnostic UI/evidence.

Actual realAI post-fix verification completed16/16 in one project, but another stopped11/15 solely because12 current proposals were already stored. Supersede only ADR0018's12-current-proposal rejection: persist every valid bounded opinion/proposal, regardless of how many are awaiting confirmation. Retain five-item page display and three-proposal lexical input selection, complete Map40nodes/120edges and its structural validation. No automatic Map extension; user confirmation/undo remains. Historical stored opinions were already not globally capped at12. Larger-library resource behavior remains unmeasured; do not claim an8GB performance guarantee.

Per-request8000input/1000output, per-project10dailyjobs, single Gateway/no retries/no fallback/default-off and user aggregate caps remain unchanged. Core minimum0tokens. Owner explicitly authorized sufficient real development tests and asked to prioritize stability/rigor; developer tests use the existing separate ledger/limits, do not change user quotas or silently enable development mode in the shipped app. Every actual request is accounted for separately from mock fixtures and predicted costs.

A second real verification exposed a semantic and structural failure: a domain application was proposed as a missing foundation, with the same existing node in both needs and required_by, making a cycle. The topology guard correctly rejected it; the failed run is retained. The owner identified overly fine, per-paper directions. Judge at reusable learning-task granularity: existing active nodes may absorb supplemental materials/methods/updates even when mastered; existing proposals absorb the same learning objective via join. Dataset, experimental object, model version, narrow method and application differences do not automatically justify new nodes. New proposals must explain a distinct capability/knowledge unit and the current route gap. Missing prerequisites must be necessary foundations, never downstream applications, and their needs cannot contain the dependents or descendants. Uncertain evidence remains unclear. This is model guidance plus unchanged local graph validation, not a deterministic guarantee of semantic accuracy. No automatic merging/deletion of existing user opinions.

Completing a job does not establish semantic correctness. Independent review of two completed real rounds found unrelated papers joined to proposals, including one rationale explicitly admitting no match. The next prompt therefore defines coverage by a learning task/capability rather than a broad goal, forbids join when no supplied proposal matches, and forbids forced grouping merely to reduce direction count or clear the queue. Lack of evidence remains unclear. Local code does not infer semantics from keywords, repair edges, change verdicts or repeat the model request. Independent semantic review is part of the current development acceptance, and earlier complete-but-wrong runs remain failures.

A subsequent independent repeat returned unclear with a valid nearby c-node reference. This is uncertain context, not a coverage claim or graph instruction. Permit nearest only for covered or unclear; validate every provided unclear nearest against the current active-node whitelist, then discard the reference before persisting/returning the uncertain opinion so it cannot create membership or a covered UI state. Other verdicts still reject inapplicable nearest, and unknown/malformed/context-external references still fail. The actual unclear verdict and reason remain unchanged. Synthetic whole-queue regressions cover both valid ancillary context and invalid refs. Needs must express necessary learning foundations; mere mentions or optional implementation examples do not establish prerequisites.

Two provider variants also invented reason_detail and reason_note with literal empty-string values. Compatibility is limited to these exact two result-group keys and exact empty strings; discard them before normalized/store/UI output. Other unknown keys and all nonempty values (including whitespace, references, ordinary prose), containers, numbers/null remain rejected. No reason-prefix wildcard, inferred defaults or field repair. This changes no judgment, topology, reference or source scope. Prior failed runs are retained.

Further real semantic review found incorrect joins despite completed jobs, broad goals used as coverage and optional methods made hard prerequisites. Do not accept these runs. Compare task action + core object + explicitly constrained method, remove only paper/dataset/application decorations, produce the reason before verdict, and default prerequisites toempty until necessity is supported. New_task parent remains mandatory; never infer it from needs. Add a complete bounded type example. Share envelope construction with growth input accounting to avoid parameter drift.
